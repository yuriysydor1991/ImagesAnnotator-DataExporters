## Розкладки згенерованих наборів даних

Кожен нащадок `LibraryContext` реалізований одним класом-експортером у [src/exporters](/src/exporters). Дана підсекція описує, що кожен із них записує у директорію, названу через `LibraryContext::set_export_path()`. Інтерфейс, який ними керує, описано у підсекції [API експортерів наборів даних](/doc/sections/uk_UA/4-project-structure/4-9-the-dataset-exporters-api.md).

### Що спільного у них усіх

- Геометрія прямокутника читається з полів `ImageRecordRect` `name`, `x`, `y`, `width` і `height`, завжди у власних піксельних координатах зображення. Розміри зображення походять з полів `ImageRecord` `iwidth` та `iheight`.
- Запис зображення, який не містить прямокутників, пропускається кожним форматом.
- Перш ніж торкнутись зображення, запис передається внутрішньому завантажувачу зображень. Запис, який вказує на вебсторінку, спершу звантажується за допомогою [libcurl](/doc/sections/uk_UA/5-project-build/5-14-enabling-libcurl.md) у тимчасовий кеш попереднього завантаження, і відтоді його `ImageRecord::get_full_path()` повертає локальну кешовану копію. Запис, який уже вказує на локальний файл, залишається без змін.
- Бібліотека самотужки не декодує жодного формату зображень. Вона копіює файли зображень як є, або просить наданий `IImageCropperFacility` створити обрізані.
- Запис, який не вдається опрацювати, потрапляє до журналу і пропускається, а сам прохід триває далі.
- Експортер YOLO v4, три експортери Ultralytics YOLO, експортер COCO, експортер Pascal VOC та експортер Create ML створюють свою директорію призначення. Для форматів простого тексту та PyTorch Vision `export_path` має існувати до виклику `export_db()`.

Усі наведені нижче приклади описують одну й ту саму базу даних із двох записів:

| Зображення | Розмір | Прямокутники |
| --- | --- | --- |
| `/home/user/images/street.png` | 640 x 400 | `dog` (50, 20, 100, 40), `dog` (300, 25, 90, 45) |
| `/home/user/images/park.jpg` | 640 x 480 | `cat` (200, 130, 48, 52), `dog` (12, 8, 64, 64) |

### PlainTxtExportLibraryContext

Найпростіша розкладка: один простий текстовий файл на кожне імʼя анотації, записаний прямо у директорію експорту й названий `<імʼя-анотації>.txt`.

```
export_path/
|-- cat.txt
`-- dog.txt
```

Файл отримує по одному рядку на кожен запис зображення, який несе принаймні один прямокутник із цим імʼям:

```
<повний шлях зображення> <кількість прямокутників> <x> <y> <width> <height> [<x> <y> <width> <height> ...]
```

Кількість - це число прямокутників із тим імʼям анотації, знайдених у тому зображенні, і саме стільки четвірок координат іде після неї. Отже `dog.txt` містить:

```
/home/user/images/street.png 2 50 20 100 40 300 25 90 45
/home/user/images/park.jpg 1 12 8 64 64
```

а `cat.txt` містить:

```
/home/user/images/park.jpg 1 200 130 48 52
```

Рядки йдуть у порядку записів у базі даних. Жоден файл зображення не копіюється і не переписується - перше поле є значенням `ImageRecord::get_full_path()`, яке для попередньо звантаженого вебзапису є шляхом його тимчасової кешованої копії. Текстовий файл із уже наявним іменем обрізається одразу як прохід експорту його відкриває.

### Yolo4ExportLibraryContext

Тренувальна директорія darknet для детектора YOLO v4. Експортер сам створює директорію експорту, якщо її ще немає, разом із субдиректоріями `data`, `cfg` і `backup`:

```
export_path/
|-- backup/
|-- cfg/
|   `-- yolov4-obj.cfg
`-- data/
    |-- obj.data
    |-- obj.names
    |-- park.jpg
    |-- park.txt
    |-- street.png
    |-- street.txt
    |-- train.txt
    `-- val.txt
```

`data/obj.names` перелічує кожне окреме імʼя анотації всієї бази даних, по одному на рядок. Перелік є впорядкованою множиною, яку повідомляє база даних, тож номер рядка імені є і його індексом класу - тут `cat` є класом `0`, а `dog` класом `1`:

```
cat
dog
```

`data/obj.data` називає кількість класів і шляхи інших файлів, усі відносно директорії експорту:

```
classes = 2
train = data/train.txt
valid = data/val.txt
names = data/obj.names
backup = backup/
```

`cfg/yolov4-obj.cfg` є цілим описом нейронної мережі детектора YOLO v4 - кістяк CSPDarknet53, шия SPP і PANet та три детектувальні голови, ті самі 162 шари мережі `cfg/yolov4-custom.cfg` самого проекту [darknet](https://github.com/yuriysydor1991/darknetxx). Нічого у ньому не треба правити руками перед тренуванням, оскільки кожне значення, що залежить від експортованого проекту, вже заповнене:

| Значення | Що записує експорт |
| --- | --- |
| `classes` кожного з трьох шарів `[yolo]` | кількість імен анотацій бази даних |
| `filters` згортки перед кожним шаром `[yolo]` | `(classes + 5) * 3` - чотири координати прямокутника, наявність обʼєкта і класи, на кожен якір |
| `max_batches` | 2000 ітерацій на клас, ніколи не менше за 6000 і ніколи не менше за кількість скопійованих експортом зображень |
| `steps` | 80% і 90% від `max_batches` |
| `width` і `height` | 832 на 832 - великий вхід, аби дрібні обʼєкти великого фото досягали детекторів |
| `subdivisions` | 32, тобто пакет із 64 зображень береться по два за раз |

Початок файлу для двох класів цього прикладу:

```
[net]
# Testing
#batch=1
#subdivisions=1
# Training
batch=64
subdivisions=32
width=832
height=832
channels=3
...
max_batches=6000
policy=steps
steps=4800,5400
```

а кінець кожного з трьох його детекторів:

```
[convolutional]
filters=21
size=1
stride=1
pad=1
activation=linear

[yolo]
mask=0,1,2
anchors=12,16, 19,36, 40,28, 36,75, 76,55, 72,146, 142,110, 192,243, 459,401
classes=2
num=9
...
```

Тренування бере директорію експорту такою, якою вона є, плюс наперед натреновані ваги кістяка [yolov4.conv.137](https://github.com/AlexeyAB/darknet/releases/download/darknet_yolo_v3_optimal/yolov4.conv.137):

```
darknet detector train data/obj.data cfg/yolov4-obj.cfg yolov4.conv.137 -map
```

Збільште `subdivisions` або зменште `width` і `height` до іншого числа, кратного 32, коли тренуванню бракує відеопамʼяті. Якорі є тими, які автори YOLO v4 отримали на наборі даних COCO; `darknet detector calc_anchors` припасовує їх до наявного набору даних.

Кожен анотований файл зображення копіюється у `data/`. Коли файл із таким іменем уже там є, копія отримує суфікс `-1`, `-2`, ... перед своїм розширенням, тож `street.png` із другої директорії-джерела опиняється там як `street-1.png`.

`data/train.txt` і `data/val.txt` обидва перелічують скопійовані зображення, по одному відносному шляху на рядок. Обидва файли записуються з однаковим вмістом, а поділ множини на справжню тренувальну і перевірочну частини залишено споживачу:

```
data/street.png
data/park.jpg
```

Кожне скопійоване зображення супроводжується файлом `data/<основа імені зображення>.txt`, який містить по одному рядку на прямокутник:

```
<індекс класу> <центр x> <центр y> <ширина> <висота>
```

Ці чотири числа нормалізовані у діапазон `0..1` відносно `iwidth` та `iheight` запису, а центром є початок прямокутника плюс половина його розміру. Рядки йдуть у порядку прямокутників усередині запису. Отже `data/street.txt` містить:

```
1 0.15625 0.1 0.15625 0.1
1 0.539062 0.11875 0.140625 0.1125
```

а `data/park.txt` містить:

```
0 0.35 0.325 0.075 0.108333
1 0.06875 0.0833333 0.1 0.133333
```

Окрім записів без прямокутників, цей експортер також пропускає записи, чиї `iwidth` або `iheight` дорівнюють нулю (нормалізація ділила б на нуль), і ті, чий файл зображення не є придатним до читання звичайним файлом або не зміг бути скопійованим. Директорія `backup/` створюється порожньою, darknet записує туди знімки своїх ваг під час тренування.

### Що спільного мають усі три розкладки Ultralytics YOLO

Три з контекстів записують розкладку, яку читає кожен випуск Ultralytics - ту, що її запровадив YOLO v5, а v8, v11 і наступні за ними зберегли. Директорія однакова для всіх трьох, як і дескриптор `data.yaml`. Від задачі змінюється лише один рядок прямокутника у файлі міток - це єдине, чим відрізняються три підсекції нижче.

Експортер сам створює директорію експорту, якщо її ще немає, разом із двома субдиректоріями:

```
export_path/
|-- data.yaml
|-- images/
|   `-- train/
|       |-- park.jpg
|       `-- street.png
`-- labels/
    `-- train/
        |-- park.txt
        `-- street.txt
```

Зображення та його анотації повʼязані шляхом: тренувальний прохід бере шлях зображення, замінює елемент шляху `images` на `labels`, а розширення - на `.txt`, і саме там читає анотації того зображення. Кожен анотований файл зображення копіюється до `images/train`. Якщо файл із таким іменем уже там є, копія отримує суфікс `-1`, `-2`, ... перед своїм розширенням - тож `street.png` із другої вихідної директорії потрапляє туди як `street-1.png` - а його файл міток слідує тому новому імені.

`data.yaml` є цілим дескриптором набору даних. Імена класів живуть у ньому, тож ця розкладка не має файлу `obj.names` розкладки darknet:

```yaml
# The Ultralytics YOLO dataset descriptor, written by the ImagesAnnotator
# annotations dataset exporters library.
#
# Drop the path line below to move this directory elsewhere: an Ultralytics
# release then takes the directory holding this very file as the dataset root.
path: '/home/user/dataset'
train: images/train
val: images/train

names:
  0: 'cat'
  1: 'dog'
```

- `path` є директорією експорту, записаною абсолютним шляхом, аби дескриптор розвʼязувався незалежно від робочої директорії тренувального проходу і від того, де фреймворк тримає власну директорію наборів даних. Прибирання цього рядка, як каже його коментар, робить директорію переносною: випуск Ultralytics тоді відступає до директорії, яка тримає сам дескриптор.
- `names` відображає індекс класу на імʼя анотації. Індекси є позиціями у відсортованій множині імен, яку повідомляє база даних, - точно тими, які несуть файли міток. Кожне імʼя записане у стилі YAML з одинарними лапками, аби двокрапка, решітка чи лапка всередині імені анотації лишалась частиною імені, а не оберталась синтаксисом.
- `train` і `val` обидва називають одну-єдину директорію `images/train`. Увесь набір пропонується і для валідації, точно як розкладка darknet записує один і той самий список у `train.txt` та `val.txt`: поділ його на справжню тренувальну і справжню валідаційну частини лишається за споживачем.

Тренувальний прохід читає експортовану директорію як є:

```
yolo detect train data=/home/user/dataset/data.yaml model=yolo11n.pt
```

із `detect`, заміненим на `obb` чи `segment` для двох інших розкладок, і моделлю, заміненою на попередньо натреновані ваги саме тієї задачі.

Усі три нормалізують прямокутник у діапазон `0..1` відносно `iwidth` та `iheight` запису, і всі три застосовують дві застороги, яких експортер darknet не має:

- **Прямокутник, який виходить за край зображення, обрізається до зображення.** Випуск Ultralytics відкидає ціле зображення через єдину координату мітки поза діапазоном `0..1`, тож прямокутник, намальований трохи за межу, інакше коштував би тому зображенню його місця у наборі даних.
- **Прямокутник, намальований справа або знизу, несе відʼємну ширину чи висоту.** Його краї впорядковуються перед обрізанням, тож він описує ту саму площу, що й намальований у зворотному напрямку.

Прямокутник, який лишився взагалі без площі всередині зображення - намальований цілком поза ним - потрапляє до журналу і відкидається, тоді як зображення і решта його прямокутників експортуються як звичайно. Записи без прямокутників і записи з нульовими `iwidth` чи `iheight` пропускаються так само, як їх пропускає кожен формат.

### UltralyticsDetectExportLibraryContext

Набір даних для детекції. Кожен прямокутник стає одним рядком з індексу класу та рамки:

```
<індекс класу> <центр x> <центр y> <ширина> <висота>
```

Це ті самі чотири нормалізовані числа, які розкладка darknet записує у власні файли міток. Тож `labels/train/street.txt` містить:

```
1 0.15625 0.1 0.15625 0.1
1 0.539062 0.11875 0.140625 0.1125
```

а `labels/train/park.txt` містить:

```
0 0.35 0.325 0.075 0.108333
1 0.06875 0.0833333 0.1 0.133333
```

### UltralyticsObbExportLibraryContext

Набір даних орієнтованих обмежувальних рамок. Кожен прямокутник стає одним рядком з індексу класу та чотирьох кутів рамки, за годинниковою стрілкою від лівого верхнього:

```
<індекс класу> <x1> <y1> <x2> <y2> <x3> <y3> <x4> <y4>
```

Тренувальний прохід обертає ті вісім чисел на власну форму з центру, розміру та кута повороту. `labels/train/street.txt` містить:

```
1 0.078125 0.05 0.234375 0.05 0.234375 0.15 0.078125 0.15
1 0.46875 0.0625 0.609375 0.0625 0.609375 0.175 0.46875 0.175
```

а `labels/train/park.txt` містить:

```
0 0.3125 0.270833 0.3875 0.270833 0.3875 0.379167 0.3125 0.379167
1 0.01875 0.0166667 0.11875 0.0166667 0.11875 0.15 0.01875 0.15
```

База даних анотацій знає лише вирівняні за осями прямокутники, тож кожна рамка, записана тут, несе кут повороту нуль. Це не даремний експорт: натренована на ньому модель OBB виявляє повернуті екземпляри тих самих обʼєктів.

### UltralyticsSegmentExportLibraryContext

Набір даних для сегментації екземплярів. Кожен прямокутник стає одним рядком з індексу класу та точок багатокутника, який окреслює обʼєкт:

```
<індекс класу> <x1> <y1> ... <xn> <yn>
```

Формат приймає багатокутник із будь-яких трьох або більше точок. Маскою прямокутної анотації є сам контур прямокутника, тож записаний багатокутник - це його чотири кути, що робить ці файли міток тотожними до наведених вище файлів орієнтованих рамок: обидва проговорюють кути одного й того самого прямокутника. Розрізняє ці дві розкладки тренувальна задача, яка їх читає: багатокутник із довільною кількістю точок тут проти чотирьох кутів повернутої рамки там.

Отже, маска завжди рівно настільки щільна, як намальований прямокутник, і натренована модель сегментації відтворює саме цю грубість. Звертайся до цієї розкладки, коли контуру прямокутника як маски достатньо, і анотуй справжніми багатокутниками у інструменті, який їх малює, коли ні.

### Формати YOLO, яких ця бібліотека не записує

Двох інших членів родини форматів YOLO навмисно лишено осторонь:

- **Розкладку пози, або ключових точок.** Її рядок мітки несе ключові точки обʼєкта після рамки, а дескриптор називає їхню кількість і пари ліво-правого дзеркала у ключах `kpt_shape` та `flip_idx`. База даних анотацій тримає іменовані прямокутники і жодних ключових точок, тож немає з чого записувати ті стовпці.
- **Розкладку класифікації**, яка є директоріями `train/<імʼя анотації>/` та `val/<імʼя анотації>/` з обрізаними зображеннями. Це описана нижче розкладка PyTorch Vision `ImageFolder` з доданою поверх неї однією директорією поділу, а поділ - це саме те, що ця бібліотека лишає своєму споживачеві.

### CocoExportLibraryContext

Набір даних для детекції об'єктів COCO: скопійовані зображення і єдиний дескриптор JSON над ними. Експортер сам створює директорію експорту, якщо її ще немає, разом із двома піддиректоріями:

```
export_path/
|-- annotations/
|   `-- instances_default.json
`-- images/
    |-- park.jpg
    `-- street.png
```

Це найширше читана розкладка бібліотеки поза тренувальним проходом YOLO. Detectron2, MMDetection, torchvision, трансформери детекції HuggingFace, CVAT, FiftyOne, Label Studio і Roboflow усі беруть цей формат, і жодному з них не треба більшого, ніж дескриптор і директорія із зображеннями:

```python
# Detectron2
from detectron2.data.datasets import register_coco_instances

register_coco_instances("my_dataset", {},
                        "/home/user/dataset/annotations/instances_default.json",
                        "/home/user/dataset/images")

# torchvision
from torchvision.datasets import CocoDetection

data = CocoDetection(root="/home/user/dataset/images",
                     annFile="/home/user/dataset/annotations/instances_default.json")
```

Кожен анотований файл зображення копіюється до `images/`. Якщо файл із таким іменем уже там є, копія отримує суфікс `-1`, `-2`, ... перед своїм розширенням, тож `street.png` з другої директорії-джерела потрапляє туди як `street-1.png`, і дескриптор називає його вже під тим новим іменем.

`annotations/instances_default.json` - це цілий дескриптор. Його пʼять ключів є тими, які визначає формат, і для наведеної вище бази даних із двох записів він виглядає так:

```json
{
"info": {"description": "The ImagesAnnotator annotations dataset", "version": "0.11.0"},
"licenses": [],
"images": [
  {"id": 1, "file_name": "street.png", "width": 640, "height": 400},
  {"id": 2, "file_name": "park.jpg", "width": 640, "height": 480}
],
"annotations": [
  {"id": 1, "image_id": 1, "category_id": 2, "bbox": [50, 20, 100, 40], "area": 4000, "iscrowd": 0, "segmentation": []},
  {"id": 2, "image_id": 1, "category_id": 2, "bbox": [300, 25, 90, 45], "area": 4050, "iscrowd": 0, "segmentation": []},
  {"id": 3, "image_id": 2, "category_id": 1, "bbox": [200, 130, 48, 52], "area": 2496, "iscrowd": 0, "segmentation": []},
  {"id": 4, "image_id": 2, "category_id": 2, "bbox": [12, 8, 64, 64], "area": 4096, "iscrowd": 0, "segmentation": []}
],
"categories": [
  {"id": 1, "name": "cat", "supercategory": ""},
  {"id": 2, "name": "dog", "supercategory": ""}
]
}
```

- **`bbox`** - це `[x, y, ширина, висота]` верхнього лівого кута, у власних пікселях зображення. Це ті самі чотири числа `ImageRecordRect`, тож тут нічого з прямокутника не нормалізується: файл міток YOLO неможливо прочитати назад у пікселі без розміру зображення, а цей дескриптор несе і те, і те.
- **`file_name`** - це саме імʼя файла, оскільки коренем набору даних читачеві передають саму директорію `images`. Сусідні `width` і `height` - це `iwidth` та `iheight` запису.
- **Ідентифікатори** усіх трьох масивів є наскрізними лічильниками того, що експорт справді записав, і починаються з `1`: читач вважає категорію `0` тлом. Тому ідентифікатор категорії - це позиція імені у впорядкованій множині, яку повідомляє база даних, плюс один - тобто індекс класу того ж імені у darknet та Ultralytics, плюс один.
- **`area`** - це `width`, помножена на `height` рамки, значення, за яким оцінювання натренованого детектора розділяє свої результати за розміром обʼєкта.
- **`iscrowd`** дорівнює `0` для кожного прямокутника: цей прапорець позначає одну анотацію, що вкриває цілий натовп обʼєктів, а іменований прямокутник бази даних анотацій ніколи таким не є.
- **`segmentation`** лишається порожнім, оскільки прямокутник не несе маски. Саме це робить експорт набором даних для детекції, а не для сегментації, і кожен читач формату сприймає порожній перелік як "маски тут немає". Бери `UltralyticsSegmentExportLibraryContext`, коли маски у формі рамки достатньо.
- Імʼя анотації та імʼя файла - обидва є текстом користувача, тож кожне з них записується екранованим за правилами JSON - лапка, зворотна скісна риска чи керівний символ усередині імені лишаються частиною імені, а не завершують рядок.

Обидва запобіжники експортерів Ultralytics діють і тут, але з іншої причини: `bbox`, що виходить за край зображення, зробив би брехнею записану поруч `area` і кожне перекриття, будь-коли обчислене проти неї.

- **Прямокутник, що виходить за край зображення, обрізається до зображення.**
- **Прямокутник, намальований справа наліво чи знизу вгору, несе відʼємну ширину чи висоту.** Його краї впорядковуються перед обрізанням, тож він описує ту саму площу, що й намальований у зворотному напрямку.

Прямокутник, у якого взагалі не лишилося площі всередині зображення, потрапляє до журналу і відкидається, тоді як зображення й решта його прямокутників експортуються як завжди. Записи без прямокутників і записи з нульовими `iwidth` чи `iheight` пропускаються так само, як їх пропускає кожен формат - і, оскільки масиви записуються після копіювання зображень, такий запис не забирає із собою жодного ідентифікатора зображення.

Увесь набір пропонується як один. Поділ його на справжню тренувальну і валідаційну частини лишається споживачеві, точно як і в кожній іншій розкладці тут.

### PascalVocExportLibraryContext

Набір даних Pascal VOC у формі директорій devkit: скопійовані зображення, по одному дескриптору XML на зображення над ними і переліки зображень, що їх називають. Експортер сам створює директорію експорту, якщо її ще немає, разом із трьома піддиректоріями:

```
export_path/
|-- Annotations/
|   |-- park.xml
|   `-- street.xml
|-- ImageSets/
|   `-- Main/
|       |-- train.txt
|       `-- val.txt
`-- JPEGImages/
    |-- park.jpg
    `-- street.png
```

Це ті самі файли, у яких LabelImg зберігає власну роботу, тож експортований проект відкривається для виправлення просто в тому анотаторі: наведи його на `JPEGImages` із `Annotations` як директорією збереження - і кожен прямокутник проекту вже там, готовий до редагування і зворотного запису. Кожен читач формату бере ті самі три директорії - `XMLDataset` з MMDetection із його типовими `img_subdir` та `ann_subdir` і `VOCDetection` з torchvision:

```python
# MMDetection
dict(type='XMLDataset',
     data_root='/home/user/dataset/',
     ann_file='ImageSets/Main/train.txt',
     data_prefix=dict(sub_data_root=''),
     metainfo=dict(classes=('cat', 'dog')))

# torchvision, який доліплює шлях VOCdevkit/VOC2012 свого року до наданого йому
# кореня, тож директорію експорту треба розмістити саме під тим іменем
from torchvision.datasets import VOCDetection

data = VOCDetection(root="/home/user", year="2012", image_set="train")
```

Кожен анотований файл зображення копіюється до `JPEGImages/`. Якщо файл із таким іменем уже там є, копія отримує суфікс `-1`, `-2`, ... перед своїм розширенням, тож `street.png` з другої директорії-джерела потрапляє туди як `street-1.png`, і його дескриптор іде за тим новим іменем. Суфікс надається за зайняту **основу** імені файла, а не лише за зайняте повне імʼя, бо це єдина розкладка, яка привʼязує дескриптор до основи: `park.jpg` і `park.png` інакше обидва просили б `Annotations/park.xml`.

`Annotations/street.xml` несе цілий опис одного зображення і його прямокутників:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<annotation>
  <folder>JPEGImages</folder>
  <filename>street.png</filename>
  <source>
    <database>The ImagesAnnotator annotations dataset</database>
  </source>
  <size>
    <width>640</width>
    <height>400</height>
    <depth>3</depth>
  </size>
  <segmented>0</segmented>
  <object>
    <name>dog</name>
    <pose>Unspecified</pose>
    <truncated>0</truncated>
    <difficult>0</difficult>
    <bndbox>
      <xmin>50</xmin>
      <ymin>20</ymin>
      <xmax>150</xmax>
      <ymax>60</ymax>
    </bndbox>
  </object>
  <object>
    <name>dog</name>
    <pose>Unspecified</pose>
    <truncated>0</truncated>
    <difficult>0</difficult>
    <bndbox>
      <xmin>300</xmin>
      <ymin>25</ymin>
      <xmax>390</xmax>
      <ymax>70</ymax>
    </bndbox>
  </object>
</annotation>
```

- **`bndbox`** - це дві кутові точки, між якими намалювали прямокутник, у власних пікселях зображення: `xmin`/`ymin` - його початок, а `xmax`/`ymax` - той початок плюс його розмір. LabelImg обертає цю пару назад на той самий прямокутник, і саме це робить міграцію двосторонньою. Координати з одиниці, які використовував початковий devkit VOC, не записуються: читач, який на них очікує - `XMLDataset` з MMDetection типово віднімає одиницю від усіх чотирьох - зсуває рамку на один піксель і зберігає її розмір, оскільки обидва кути рухаються разом.
- **`name`** - це імʼя анотації, записане як є. Це одна з двох розкладок бібліотеки, які нічого не нумерують - друга є розкладкою Create ML, - тож позиція імені у впорядкованій множині, яку повідомляє база даних, тут не вирішує нічого, а додавання імені до проекту не перенумеровує жодного вже експортованого файла.
- **`folder`** і **`filename`** - це директорія, що містить зображення, та імʼя його файла, які читач доліплює до наданого йому кореня набору даних. `width` і `height` з `size` - це `iwidth` та `iheight` запису.
- **`depth`** дорівнює `3` для кожного зображення. `ImageRecord` не несе кількості каналів, а формат не лишає способу записати розмір без неї.
- **`truncated`** дорівнює `1` рівно тоді, коли край зображення справді обрізав прямокутник, що прапорець і означає: обʼєкт продовжується поза картинкою. Прямокутник, намальований цілком усередині зображення, отримує `0`.
- **`difficult`** дорівнює `0` для кожного прямокутника - база даних не має такої позначки, а стандартне оцінювання VOC узагалі вилучає `1` зі своїх результатів. **`pose`** дорівнює `Unspecified`, оскільки кута огляду теж ніде не зберігається.
- **`segmented`** дорівнює `0`: цей прапорець обіцяє маску в директоріях сегментації devkit, а прямокутник її не несе. Бери `UltralyticsSegmentExportLibraryContext`, коли маски у формі рамки достатньо.
- Імʼя анотації та імʼя файла - обидва є текстом користувача, тож обидва записуються екранованими за правилами XML - `&`, `<` чи `>` усередині імені лишаються частиною імені, а не відкривають розмітку. Керівні символи, які XML 1.0 не має способу записати взагалі, навіть числовим посиланням, вилучаються з імені, а не потрапляють у файл, що його не прийняв би жоден парсер.

`ImageSets/Main/train.txt` і `ImageSets/Main/val.txt` обидва перелічують основи імен скопійованих зображень, по одній на рядок:

```
street
park
```

Обидва файли записуються з однаковим вмістом, точно як розкладка darknet записує один і той самий перелік у свої власні `train.txt` та `val.txt`: поділ набору на справжню тренувальну і валідаційну частини лишається споживачеві. А от їхні імена не є вільними - читач цього формату просить поділ за іменем, і `train`, `val` та `trainval` є тими, які він приймає.

Обидва запобіжники експортерів Ultralytics діють і тут:

- **Прямокутник, що виходить за край зображення, обрізається до зображення**, оскільки `bndbox`, який називає пікселі, яких у зображенні немає, є рамкою, що її жоден читач не виріже. Те, що лишається після обрізання, позначається наведеним вище прапорцем `truncated`.
- **Прямокутник, намальований справа наліво чи знизу вгору, несе відʼємну ширину чи висоту.** Його краї впорядковуються перед обрізанням, тож він описує ту саму площу, що й намальований у зворотному напрямку, а саме лише впорядкування ніколи не встановлює `truncated`.

Прямокутник, у якого взагалі не лишилося площі всередині зображення, потрапляє до журналу і відкидається, тоді як зображення й решта його прямокутників експортуються як завжди - зображення, у якого відкинули кожен прямокутник, усе одно потрапляє до переліків із дескриптором без жодного елемента `object`. Записи без прямокутників і записи з нульовими `iwidth` чи `iheight` пропускаються так само, як їх пропускає кожен формат.

Одне обмеження належить читачеві, а не експорту: `XMLDataset` з MMDetection будує шлях до зображення, доліплюючи `.jpg` до імені з переліку, тож проект із зображень PNG він прочитає лише після того, як тому класу скажуть інше. Самі дескриптори називають справжній файл своїм елементом `filename`, і кожен інший читач формату користується саме ним.

### CreateMLExportLibraryContext

Набір даних для детекції об'єктів Create ML: скопійовані зображення і єдиний дескриптор JSON поруч із ними, в одній пласкій директорії. Експортер сам створює директорію експорту, якщо її ще немає, і не робить під нею жодної піддиректорії:

```
export_path/
|-- annotations.json
|-- park.jpg
`-- street.png
```

Ця пласкість є самим форматом, а не спрощенням. Це джерело даних [`directoryWithImagesAndJsonAnnotation`](https://developer.apple.com/documentation/createml/building-an-object-detector-data-source) з `MLObjectDetector` від Apple - директорія зображень, що містить **рівно один** файл анотацій JSON, - і саме її споживає застосунок Create ML, коли теку кидають до його тренувального лотка. Ніщо інше в цій бібліотеці не розкладає свої зображення таким чином, і ніщо інше тут не веде до моделі, яка працює на iPhone: тренувальний прохід над цією директорією дає детектор Core ML.

```swift
// API Create ML над тією самою директорією, яку записав експорт
import CreateML

let source = MLObjectDetector.DataSource.directoryWithImagesAndJsonAnnotation(
    at: URL(fileURLWithPath: "/home/user/dataset"))

let detector = try MLObjectDetector(trainingData: source)

try detector.write(to: URL(fileURLWithPath: "Detector.mlmodel"))
```

Кожен файл анотованого зображення копіюється до самої директорії експорту. Коли файл із таким іменем там уже є, копія отримує суфікс `-1`, `-2`, ... перед розширенням, тож `street.png` із другої директорії-джерела потрапляє туди як `street-1.png`, і дескриптор називає його під тим новим іменем. Імʼя `annotations.json` зарезервоване тим самим механізмом: запис зображення, справді названий так, записується як `annotations-1.json`, бо другий файл JSON у директорії - це те, що це джерело даних відмовляється читати.

`annotations.json` є цілим дескриптором - один масив, по одному елементу на зображення. Для бази даних із двох записів вище він має вигляд:

```json
[
  {"imagefilename": "street.png", "annotation": [
    {"label": "dog", "coordinates": {"x": 100, "y": 40, "width": 100, "height": 40}},
    {"label": "dog", "coordinates": {"x": 345, "y": 47.5, "width": 90, "height": 45}}
  ]},
  {"imagefilename": "park.jpg", "annotation": [
    {"label": "cat", "coordinates": {"x": 224, "y": 156, "width": 48, "height": 52}},
    {"label": "dog", "coordinates": {"x": 44, "y": 40, "width": 64, "height": 64}}
  ]}
]
```

- **`x` та `y` є центром рамки**, а не її кутом, відлічені у власних пікселях зображення від його лівого верхнього краю. Це єдине місце в бібліотеці, де центр записується без подальшої нормалізації: `MLObjectDetector.DataSource.boundingBox` читається з `units: .pixel`, `origin: .topLeft` та `anchor: .center`, і саме ці усталені значення використовує застосунок Create ML. Те саме ділення навпіл потрапляє до файлів міток трьох `Ultralytics*`, лише поділене там на розмір зображення.
- **Центр припадає на півпікселя щоразу, коли розмір рамки непарний**, як показує другий `dog` зі `street.png` своїм `47.5`. Це поле є числом JSON, і формат приймає там десятковий дріб, тож половина записується, а не заокруглюється до рамки, зміщеної на піксель.
- **`width` і `height`** є розміром рамки у тих самих пікселях, полями `ImageRecordRect` без змін.
- **`label`** є іменем анотації, записаним як є. Тут ніщо не нумерується, тож - як і в розкладці Pascal VOC, і на відміну від кожної розкладки YOLO - позиція імені у впорядкованій множині, яку повідомляє база даних, не вирішує нічого, і додане до проекту імʼя не перенумеровує нічого експортованого раніше.
- **`imagefilename`** є самим лише іменем файлу, оскільки джерелу даних вказують на директорію, що містить і зображення, і цей дескриптор. Зверни увагу на однину як цього ключа, так і `annotation`: саме її документує Apple, а множинна пара `image` / `annotations`, яку видають деякі конвертери, є іншим діалектом формату.
- Імʼя анотації та імʼя файлу є користувацьким текстом, тож кожне з них записується з екрануванням JSON - лапка, зворотна скісна риска чи керівний символ усередині імені лишається частиною імені, а не завершує рядок.

Обидва запобіжники експортерів Ultralytics діють і тут, а важать вони саме через центр: його беруть після обрізання, оскільки центр, обчислений над необрізаною рамкою, не мусить лежати всередині рамки, яку отримує читач.

- **Прямокутник, що виходить за край зображення, обрізається до зображення.**
- **Прямокутник, намальований справа або знизу, несе відʼємну ширину чи висоту.** Його краї впорядковуються перед обрізанням, тож він описує ту саму площу, що й намальований у зворотному напрямку.

Прямокутник, у якого зовсім не лишилося площі всередині зображення, логується і відкидається, тоді як зображення і решта його прямокутників експортуються як зазвичай - зображення, кожен прямокутник якого відкинули, все одно потрапляє до дескриптора з порожнім масивом `annotation`. Записи без прямокутників, а також записи з нульовими `iwidth` чи `iheight`, пропускаються так само, як їх пропускає кожен формат.

Увесь набір пропонується як один набір даних, так само як його пропонує кожна інша розкладка тут. Це єдине місце, де це нічого не коштує споживачеві: застосунок Create ML усталено має `Automatic` для даних перевірки і сам утримує невелику частину поданого набору, тож директорія, записана цим експортером, є повною як є.

### PyTorchExportLibraryContext

Класифікаційна розкладка, яку читає набір даних `ImageFolder` з PyTorch Vision: одна директорія на імʼя анотації, яка містить зображення, обрізані до прямокутників із тим іменем.

```
export_path/
|-- cat/
|   `-- park.jpg
`-- dog/
    |-- park.jpg
    `-- street.png
```

Імʼя анотації вживається дослівно як імʼя директорії, і директорія створюється, якщо її ще немає. Сама директорія експорту не створюється, вона має існувати заздалегідь.

Це єдиний формат, якому потрібен обрізач із `PyTorchExportLibraryContext::set_cropper()`: без нього `export_db()` заносить це до журналу і одразу повертає `false`. Для кожного прямокутника експортер викликає

```cpp
cropper->crop_out_2_fs(ir, irr, tofpath);
```

де `tofpath` встановлено у `<export_path>/<імʼя анотації>/<імʼя файлу зображення>`. Реалізація вільна переписати той шлях, наприклад щоб дописати розширення формату, у який вона кодує. Прямокутники з порожнім іменем анотації пропускаються.

Бібліотека тут взагалі не виконує декодування зображень - обрізаний файл є цілком роботою наданого обрізача, а його значення, що повертається, вирішує чи вважається прямокутник експортованим. Зверни увагу, що всім прямокутникам одного імені анотації всередині одного зображення пропонується один і той самий шлях призначення, тож обрізач, який має тримати їх окремо, має сам зробити шлях унікальним. Переглянь підсекцію [API експортерів наборів даних](/doc/sections/uk_UA/4-project-structure/4-9-the-dataset-exporters-api.md) для начерку реалізації.
