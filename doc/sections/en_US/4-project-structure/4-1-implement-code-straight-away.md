## Where the exporters implementation lives

A call chain through the library is short. A consumer fills the `IADataExportersContext` descendant of the wanted layout, hands it to `IADataExportersLib::perform_export()` and gets the dataset written to the directory it named through `IADataExportersContext::set_export_path()`:

- [src/lib/facade/IADataExportersFacade.cpp](/src/lib/facade/IADataExportersFacade.cpp) - the installed facade. Every static method simply asks `iade0impl::LibFactory` for the requested object, so that no implementation type appears in a public header.
- [src/lib/facade/IADataExportersContext.cpp](/src/lib/facade/IADataExportersContext.cpp) - the accessors of the installed `IADataExportersContext`, whose data members are private. It is named by the `IADE_FACADE_SRC` list of [src/CMakeLists.txt](/src/CMakeLists.txt), so every test executable driving a context compiles it the way the library target does.
- [src/lib/libmain/LibMain.cpp](/src/lib/libmain/LibMain.cpp) - the only `IADataExportersLib` implementation. `LibMain::perform_export()` creates the exporter of the given context, publishes it back through `ctx->set_exporter()` and calls `IExporter::export_db()` with that very same context.
- [src/lib/libmain/LibFactory.cpp](/src/lib/libmain/LibFactory.cpp) - the factory. `LibFactory::create_exporter()` maps the type of the given context onto a concrete exporter with one `std::dynamic_pointer_cast` per layout, and returns a `nullptr` for a context naming no known layout.
- [src/lib/facade/public](/src/lib/facade/public) - the `IADataExportersContext` descendants: `PlainTxtExportContext`, `Yolo4ExportContext`, `UltralyticsDetectExportContext`, `UltralyticsObbExportContext`, `UltralyticsSegmentExportContext`, `CocoExportContext`, `PascalVocExportContext`, `CreateMLExportContext`, `Dxxwjz2ExportContext`, `Dxxwjz3ExportContext`, `Dxxwjz2pExportContext`, `Dxxwjz3pExportContext` and `PyTorchExportContext`. Each is an installed header only class which inherits the whole of `IADataExportersContext` - the type itself is what names the layout, so no exporter has to appear in the public interface. Twelve of them add nothing at all; `PyTorchExportContext` adds the image cropper its layout is the only one to need.
- [src/exporters](/src/exporters) - one sub-directory per dataset layout family, each a sub-component of its own with its sources, its `CMakeLists.txt` and its unit tests: [PlainTxt](/src/exporters/PlainTxt) holds `PlainTxt2FolderExporter`, [Yolo4](/src/exporters/Yolo4) holds `Yolo42FolderExporter` together with the `Yolov4CfgWriter` it hands its `cfg/yolov4-obj.cfg` stream to - the comment head of which names the command line the network is trained with, the darknet one of the YOLO v4 directory unless the darknetxx projects name their own - [Ultralytics](/src/exporters/Ultralytics) holds the abstract `Ultralytics2FolderExporter` - which writes the directory and the `data.yaml` descriptor all three YOLO tasks share - with its `UltralyticsDetect2FolderExporter`, `UltralyticsObb2FolderExporter` and `UltralyticsSegment2FolderExporter` specialisations, [Coco](/src/exporters/Coco) holds `Coco2FolderExporter`, [PascalVoc](/src/exporters/PascalVoc) holds `PascalVoc2FolderExporter`, [CreateML](/src/exporters/CreateML) holds `CreateML2FolderExporter`, [Darknetxx](/src/exporters/Darknetxx) holds the four darknetxx exporters with the writers of their documents - `Dxxwjz2FolderExporter`, the `Yolo42FolderExporter` descendant which adds the dxxwjz2 network to train of the `Dxxwjz2NetworkWriter` to the YOLO v4 directory, its `Dxxwjz3FolderExporter` descendant of the dxxwjz3 network of the `Dxxwjz3NetworkWriter` (the `Dxxwjz2NetworkWriter` descendant of the network cfg of the JSON values of the `Dxxwjz3CfgJson`), the `Dxxwjz2pProjectExporter` of the dxxwjz2p training project of the `Dxxwjz2pProjectWriter` and its `Dxxwjz3pProjectExporter` descendant of the dxxwjz3p one of the `Dxxwjz3pProjectWriter`, the two project writers sharing the annotations member of the `Dxxwjz2pAnnotationsWriter` - and [PyTorch](/src/exporters/PyTorch) holds `PyTorchVisionFolderExporter`. All of them stay in the `iannotator::exporters` namespace. `ExportersAliases.h` remains at the component root, since every one of them shares it: it pulls the installable interface names and the data drivers record names into that namespace, so the moved application code keeps referring to them unqualified.
- [src/helpers](/src/helpers) - shared by every exporter: `ImageRecordUrlAndPathHelper` decides whether a record points at a local file or at a URL, `ImageLoader` preloads a web hosted record into a local cache directory, `TypeHelper` shortens the numeric conversions the coordinate maths needs.
- [src/zlib](/src/zlib) - the `ZlibController` of the zlib, the controller component of the [cpp-app-template](https://github.com/yuriysydor1991/cpp-app-template) `appZlib` branch in the adaptation the darknetxx made of it, which writes the gzip compressed files of the layouts which ask for them - the darknetxx ones.
- [src/CURL](/src/CURL) - `CURLController`, the libcurl wrapper `ImageLoader` downloads through.

The helper and CURL namespaces are nested under `iannotator::exporters` on purpose. The data drivers library carries top level namespaces of the same names, and both libraries end up in the same process.

### Adding a new export format

1. Implement `IExporter::export_db()` in a new class under a new sub-directory of [src/exporters](/src/exporters), named after the layout the way `PlainTxt`, `Yolo4`, `Ultralytics`, `Coco` and `PyTorch` are. Include `ExportersAliases.h`, keep the class in the `iannotator::exporters` namespace and do not mark it with `IADE_API` - the exporters stay private to the shared object and are reached through `IExporter` only. Should the format need data of its own - cropped images, the way the PyTorch Vision layout does - declare it on the context descendant below and reach it with a `std::dynamic_pointer_cast` of the given context.
1. Declare a new `IADataExportersContext` descendant in [src/lib/facade/public](/src/lib/facade/public), copying one of the existing headers. It stays empty unless the layout asks for data no other one needs, in which case it carries the accessors of that data - see `PyTorchExportContext` and its `src/lib/facade` source, which the `IADE_FACADE_SRC` list names. Mark it `IADE_API` - the cast below needs its typeinfo to leave the shared object.
1. Add a `std::dynamic_pointer_cast` for it to `iade0impl::LibFactory::create_exporter()` in [src/lib/libmain/LibFactory.cpp](/src/lib/libmain/LibFactory.cpp), returning the new exporter.
1. Give the layout a factory method of its own - a `create_<layout>_library_context()` on `iade0impl::LibFactory` and the `IADataExportersFacade` one-liner forwarding to it - the way every other layout has one, so a consumer never has to name the descendant itself. The mocked `LibFactory` of [src/lib/facade/tests/mocks](/src/lib/facade/tests/mocks) carries a `MOCK_METHOD` per factory method, so it gains one too.
1. Give the new sub-directory a `CMakeLists.txt` with the `target_sources()` call of its own sources and an `add_subdirectory(tests)`, then `add_subdirectory()` it from [src/exporters/CMakeLists.txt](/src/exporters/CMakeLists.txt). Declare its source list in [src/CMakeLists.txt](/src/CMakeLists.txt) next to `IADE_PLAIN_TXT_SRC`, `IADE_YOLO4_SRC`, `IADE_ULTRALYTICS_SRC`, `IADE_COCO_SRC` and `IADE_PYTORCH_SRC`, and append it to the `IADE_EXPORTERS_SRC` union - those lists are what the test executables compile from.
1. Add a `tests/unit/<YourExporter>` tree inside the new sub-directory, the way each layout carries its own. Copying the whole `tests` directory of one of the existing sub-components is the quickest start - see [Project tests](/doc/sections/en_US/4-project-structure/4-4-project-tests.md).

The library decodes no image format of its own. Anything that needs pixels - the cropping of the PyTorch vision layout - is delegated to the `IImageCropperFacility` implementation supplied by the consumer.
