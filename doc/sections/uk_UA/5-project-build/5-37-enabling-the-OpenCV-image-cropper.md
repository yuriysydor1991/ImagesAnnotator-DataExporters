## Вмикання обрізача зображень на OpenCV

Бібліотека не декодує жодного власного формату зображень. Саме тому існує `PyTorchExportLibraryContext::set_cropper()`: [експорт PyTorch Vision](/doc/sections/uk_UA/4-project-structure/4-10-the-produced-dataset-layouts.md) має вирізати анотовані прямокутники із зображень і просить свого споживача зробити це тим набором засобів роботи із зображеннями, який той проект уже лінкує - обрізачем GTKmm, Qt чи wxWidgets застосунку ImagesAnnotator, наприклад.

Споживач, якому нічого позичити, лишався ні з чим. Тому, коли збірка знаходить OpenCV, бібліотека несе і власний обрізач, і такому споживачеві не потрібно надавати нічого.

### Опція

```
cmake -S . -B build -DENABLE_OPENCV=ON
```

`ENABLE_OPENCV` за умовчанням `ON`, і `ON` означає *перевірити*, а не *вимагати*. Залежність необов'язкова в обидва боки:

| Ситуація | Наслідок |
| --- | --- |
| OpenCV встановлено | обрізач вкомпільовано, бібліотека лінкує `core` та `imgcodecs` |
| OpenCV не встановлено | конфігурація завершується успішно, друкує причину, бібліотека збирається без обрізача |
| `-DENABLE_OPENCV=OFF` | перевірку пропущено взагалі, наслідок той самий |

Ніщо з цього не провалює конфігурацію. Відсутність OpenCV означає лише, що експорт і надалі просить обрізача у свого споживача - точно так, як було до появи цього обрізача.

Вкажи перевірці власний префікс через `-DOpenCV_DIR=<тека>`, коли встановлення не в типовому системному місці, і зміни перелік потрібних компонентів через `-DTEMPLATE_APP_OPENCV_COMPONENTS="core;imgcodecs"`.

### Який обрізач використає експорт

Правило в один рядок: **наданий тобою обрізач завжди перемагає.**

1. Обрізач передано через `PyTorchExportLibraryContext::set_cropper()` - використано саме той обрізач. Проект, який уже декодує зображення власним способом, продовжує робити рівно це, є в бібліотеки OpenCV чи немає.
1. Місце обрізача лишили порожнім, а бібліотека має обрізач на OpenCV - експорт бере його, і налаштовувати не довелось нічого.
1. Місце обрізача лишили порожнім, і бібліотека не має обрізача - експорт завершується невдачею із відповідним записом у журналі, і це та поведінка, яка передувала цій можливості.

Тож наявний споживач не бачить жодної зміни, а новий може просто не чіпати це поле.

### Прямий запит

`LibraryFacade::create_image_cropper()` видає той самий обрізач або `nullptr` у збірці без OpenCV. Це і є спосіб дізнатись, чи має збірка обрізач:

```cpp
namespace iade = ImagesAnnotatorDataExporters011;

auto ctx = std::make_shared<iade::PyTorchExportLibraryContext>();
ctx->set_export_path("/tmp/pytorch-dataset");
ctx->set_db_provider(db);

// Необов'язково. Якщо поле не чіпати, буде використано той самий обрізач.
ctx->set_cropper(iade::LibraryFacade::create_image_cropper());

if (ctx->get_cropper() == nullptr) {
  // Ця збірка без OpenCV - надай власний обрізач або обери формат
  // експорту, якому обрізач не потрібен.
}
```

### Що він робить

`crop_out_2_fs()` декодує назване записом зображення, вирізає прямокутник і записує його у форматі PNG:

- прямокутник, що виходить за край, **обрізається** до меж зображення, тож записується його перекривна частина, а не відбувається невдача виклику - так само роблять власні обрізачі застосунку;
- прямокутник, що цілком лежить поза зображенням, провалює виклик;
- шлях призначення переписується на розширення `.png`, з яким би він не надійшов;
- наявний файл призначення ніколи не перезаписується - додається суфікс `-0`, `-1`, ... доки не знайдеться вільне ім'я.

Жоден тип OpenCV не з'являється у жодному встановлюваному заголовку. Обрізач доступний через абстрактний `IImageCropperFacility` так само, як будь-який наданий споживачем, тож **проекту-споживачу цієї бібліотеки не потрібен власний OpenCV**, навіть коли бібліотеку зібрано з ним.

### Тести

`UTEST_OpenCVImageCropper` покриває обрізач і конфігурується лише у збірці, яка знайшла OpenCV, оскільки кожен його випадок працює саме з ним. Збірку без OpenCV покриває `UTEST_LibFactory.create_image_cropper_matches_what_the_build_found`, який стверджує, що фабрика там не видає нічого, і `UTEST_PyTorchVisionFolderExporter.handles_a_missing_cropper_by_the_build`, який стверджує, що без обрізача експорт провалюється, а із вбудованим - завершується успішно.
